# 文本测试三种指标统计方式对比

本文档说明测试系统中三种指标统计体系的数据源、计算方式、优点与局限性，用于解读测试报告时区分口径差异。

- **服务端指标区**：测试状态区（实时，标题"vLLM 指标（快照）"）与测试报告区（整轮汇总，标题"服务端指标"，按 业务/技术/资源/统计 四组展示）
- **监控区**：Prometheus 快照时序图与统计卡片
- **case e2e 统计**：每个 case 弹窗中的端到端性能

报告模式四组划分：

| 分组 | 指标 | 数据源 |
|---|---|---|
| 业务指标 · 时延与并发 | 平均首 token/逐 token/端到端延迟、运行中/排队请求峰值 | vLLM counter 差分 |
| 技术指标 · 吞吐与引擎 | 平均生成吞吐、Prefill/Decode 耗时、KV 缓存占用、前缀缓存命中、累计抢占 | vLLM counter 差分 |
| 资源指标 · GPU 显存 | 显存使用率、显存控制器使用率（各卡平均） | Prometheus（DCGM，快照/实时查询 stats） |
| 统计指标 · Token 累计 | 累计输入/生成 tokens | vLLM counter 差分 |

其中端到端延迟来自 vLLM `e2e_request_latency_seconds`（请求到达前端 → 收到最后一个 token，含 tokenize/排队全程，较新 vLLM 才暴露）；资源指标两个显存项来自 dcgm-exporter（`DCGM_FI_DEV_FB_USED/(USED+FREE)` 与 `DCGM_FI_DEV_MEM_COPY_UTIL`），非 vLLM 暴露，Prometheus 不可达或未部署 dcgm-exporter 时显示 "—"。

## 1. vLLM 指标区（服务端 counter 差分）

### 数据源

直连 vLLM 服务的 `/metrics` 端点（Prometheus 文本格式），不经 Prometheus 中转。

- 抓取：`app/llm_client.py::fetch_vllm_metrics`
- 解析提取：`app/llm_client.py::extract_vllm_metrics`（兼容新旧 vLLM 指标命名）
- 轮询：`app/test_engine.py::_poll_vllm_metrics`，测试运行期间**每 5 秒采样一次**

### 计算方式

| 指标类型 | 计算方式 |
|---|---|
| gauge 类（运行中/排队请求、KV 缓存占用） | 直接取当前值 |
| counter 类（tokens、TTFT/TPOT 的 sum/count、前缀缓存 hits/queries、抢占次数） | 扣除**本轮首次采样时的基线**，得到本轮差分值；vLLM 中途重启 counter 归零时自动重校准 |
| 平均首字/逐 token 延迟 | 本轮 `sum` 差分 ÷ 本轮 `count` 差分 |
| 前缀缓存命中率 | 本轮 `hits` 差分 ÷ 本轮 `queries` 差分 |
| 生成吞吐 | `generation_tokens_total` 相邻两次采样差分 ÷ 采样间隔（新版 vLLM 已移除吞吐 gauge） |

报告模式的整轮汇总（`_vllm_metrics_summary`）：

- 运行中/排队请求 → 取**峰值**
- 吞吐/缓存占用（gauge 类）→ 取**采样点平均**（各采样点等权）
- **平均首字/逐 token 延迟、前缀缓存命中率 → 取最后一次快照的 counter 差分之比（终值差分，请求等权）**；测试结束时会补一次最终抓取（`_wait_all`），保证覆盖最后一批完成的请求；终值缺失（最终抓取失败）时回退采样点平均
- 累计输入/生成 tokens、累计抢占次数 → 取最后一次快照（本轮差分累计值）

### 优点

- **算术精确**：TTFT/TPOT 均值来自 `sum/count` counter 差分，无插值、无窗口假设
- **请求等权**：报告均值是终值差分（`sum_T_end/count_T_end`），即按请求等权的真均值，不受指标随时间漂移影响（历史 bug 见案例四）
- **服务端视角**：能看到排队深度、KV 缓存占用、抢占次数等引擎内部状态，是唯一能观察服务端排队/调度行为的来源
- **基线隔离**：counter 扣基线后只反映本轮测试，不受服务启动以来历史负载污染
- **无外部依赖**：只要 vLLM 服务可达即可，不依赖 Prometheus 部署

### 局限性

- **采样粒度 5 秒**：请求峰值取自采样点，两个采样点之间的瞬时尖峰会被漏掉；终值差分依赖测试结束时的最终抓取，若该次抓取失败则回退采样点平均（此时均值退化为时间加权，见案例四）
- **吞吐为瞬时速率的均值**：每个采样点的吞吐是 5 秒窗口速率，整轮平均对突发不敏感（这通常正是想要的，但需知晓口径）
- **依赖指标命名兼容**：vLLM 版本间指标改名（如 `gpu_cache_usage_perc` → `kv_cache_usage_perc`）需要代码适配
- **无分布信息**：counter 只有 sum/count，算不出 p50/p95 等分位数（报告中的拟合分位数来自 TTFT 直方图桶，见下文）

## 2. 监控区（Prometheus 快照）

### 数据源

Prometheus server 的 `query_range` API，测试结束时按起止时间一次性拉取时序数据，存档为 `workspace/<任务名>/metrics.json`（无快照时回退实时查询，受 TSDB 保留期限制）。

- 拉取与存档：`app/prom_snapshot.py::fetch_snapshot`
- 统计卡片：`app/prom_snapshot.py::_compute_stats`

### 计算方式（PromQL）

| 指标 | PromQL | 说明 |
|---|---|---|
| 运行中/排队请求、KV 缓存占用 | 直接查询 gauge | 原始时序 |
| 生成吞吐 | `rate(generation_tokens_total[1m])` | **1 分钟滑动窗口**速率 |
| TTFT p50/p95 | `histogram_quantile(q, sum by (le) (rate(bucket[30s])))` | **30 秒窗口** + 直方图桶内**线性插值** |
| 请求抢占速率 | `rate(num_preemptions_total[1m])` | **1 分钟滑动窗口**速率；>0 表示 KV cache 耗尽触发调度器抢占（精确累计次数见 vLLM 指标区的"累计抢占次数"） |

统计卡片对时序取 avg/peak（如"平均 TTFT p50"是各窗口 p50 估计值的时序平均）；抢占卡片优先显示报告的精确累计次数（vLLM counter 差分），无该数据时回退抢占速率峰值。

### 优点

- **完整时序曲线**：能看到负载爬坡、抖动、稳态形态，是三种方式中唯一提供"过程"而非"结果"的
- **可回溯**：快照存档后报告可随时重看（在 TSDB 保留期内甚至可重新查询）
- **生态联动**：可与 Grafana 面板、DCGM GPU 指标等关联分析，定位"慢是 GPU 瓶颈还是调度瓶颈"
- **不侵入测试流程**：采集发生在测试工具之外，测试工具崩溃也不丢监控数据

### 局限性

- **直方图插值误差（最重要）**：vLLM 的 TTFT 直方图桶边界固定（…0.1 → 0.25 → 0.5…），0.1~0.25s 之间是一个 150ms 宽的大桶。`histogram_quantile` 假设桶内均匀分布做线性插值，真实值落在该桶内时分位数估计误差可达 ±75ms。典型症状：p50 曲线钉死在桶中点 175ms 不动
- **rate 窗口效应**：`rate[1m]` 向前回看 60 秒。测试时长不足 1 分钟时窗口伸入测试前的空闲时段，吞吐被严重稀释（实测案例：57.8s 测试中监控区平均吞吐 179 tok/s，真实值约 349 tok/s）
- **窗口平滑**：30s/1m 窗口会平滑掉突发，峰值吞吐被低估
- **抓取间隔粒度**：受 Prometheus 抓取周期（通常 15s）限制，时间对齐存在偏差
- **依赖部署**：需要 Prometheus 正确抓取 vLLM 指标，是外部依赖

## 3. case e2e 统计（客户端实测）

### 数据源

测试工具客户端在**每次流式调用中自行打点**，不依赖任何服务端指标。

- 打点字段：`req_t0`（请求发出）、`first_chunk_at`（首 chunk 到达）、`last_chunk_at`（末 chunk 到达）、`chars`、`first_chunk_chars`
- 实现位置：`app/test_engine.py::CaseState`（`finish_qa` 中固化，`to_dict` 中聚合）

### 计算方式（单请求）

```
TTFT      = first_chunk_at - req_t0                    # 首字延迟（秒）
TPOT      = (last_chunk_at - first_chunk_at)
            / (chars - first_chunk_chars)              # 逐字间隔（秒/字符）
吞吐      = chars / (last_chunk_at - req_t0)           # 单请求（字符/秒）
```

case 级聚合：

```
ttft_avg_s    = Σ TTFT / 请求数                        # 按请求等权平均
ttft_max_s    = max(TTFT)
tpot_avg_s    = Σ TPOT / 请求数
throughput_cps = 总字符 / 总生成时段                    # 纯生成吞吐（不含首字等待）
```

> **TTFT 计时起点**：`req_t0` 在发起 HTTP 请求前记录。若底层每次请求新建 TCP 连接，则 e2e TTFT 额外包含 TCP 握手时间；连接复用（keep-alive）后仅含请求传输与响应回程（详见案例三）。

### 优点

- **用户真实视角**：包含网络传输、服务端排队、客户端调度在内的完整链路延迟，回答的是"用户感受到多快"
- **逐请求精确打点**：无插值、无窗口、无采样间隔，单请求粒度的真值
- **保留原始样本**：`e2e_ttft` 列表存有每个请求的 TTFT，具备计算任意分位数的潜力（当前仅展示均值/最大值）
- **无外部依赖**：不依赖 vLLM 版本、Prometheus 部署
- **可定位客户端侧问题**：服务端指标正常而 e2e 指标差时，可推断问题在网络或客户端

### 局限性

- **单位是字符不是 token**：TPOT/吞吐按字符计算，与 vLLM 指标区的 token 口径不可直接对比（实测中文场景 1 token ≈ 1.67 字符，即字符口径延迟 ≈ token 口径延迟 ÷ 1.67）
- **TTFT 含 TCP 连接建立开销**：`req_t0` 在建立连接之前记录，若每次请求新建 TCP 连接，e2e TTFT 会比服务端口径系统性偏高（实测 ~10-20ms/请求，见案例三；2026-08-27 起已改为连接复用，该开销基本消除）
- **TPOT 受首 chunk 字符数影响**：分母是 `chars - first_chunk_chars`，首 chunk 携带字符多时 TPOT 偏大
- **只统计流式文章调用**：内部 QA 调用（如名词生成阶段）不计入 e2e
- **case 独立视角**：聚合发生在单 case 内，无跨 case 的全局 e2e 汇总
- **客户端时钟与调度开销**：asyncio 事件循环繁忙时 chunk 到达时刻的记录可能有毫秒级延迟，高并发下客户端本身可能成为瓶颈，此时 e2e 指标反映的是"客户端+链路"而非纯服务端能力

## 4. 横向对比

| 维度 | vLLM 指标区 | 监控区 | case e2e |

| 时序过程 | 无（仅快照序列） | 有（完整曲线） | 无 |
| 外部依赖 | vLLM 可达 | Prometheus 部署 | 无 |

## 5. 典型差异案例解读

**案例一：平均生成吞吐 364 vs 179 tok/s（vLLM 指标区 vs 监控区）**
测试时长 57.8s < `rate[1m]` 的 60s 窗口，每个采样点的窗口都伸入测试前的空闲时段，吞吐被稀释约一半。vLLM 指标区的 5 秒差分不受影响。**短测试（<1 分钟）时监控区吞吐不可信。**

**案例二：平均首字延迟 121ms vs 173.8ms（vLLM 指标区 vs 监控区 TTFT p50）**
真实 TTFT 集中在 ~120ms，全部落在 vLLM 直方图 0.1~0.25s 的宽桶内。`histogram_quantile` 线性插值把 p50 估计为桶内位置，曲线钉死在桶中点 175ms。**分位数落在宽桶内时监控区 TTFT 分位数不可信，误差上限为桶宽的一半。**

**案例三：平均 TTFT 167.5ms vs 130ms（case e2e vs vLLM 指标区）**

两边统计的是同一批 800 个请求（token 数核对：prompt 23802 ≈ 800×30 tok，generation 994477 ≈ 800 篇×2000 字 ÷ 1.67 字/tok），37.5ms 的差距全部来自**计时起点与链路开销**：

```
客户端 TTFT = TCP 握手 + 请求上行 + 服务端处理 + 响应下行 + 客户端调度
服务端 TTFT = 服务端处理（从请求到达引擎起算）
```

机制与证据：

1. **每请求新建 TCP 连接**：旧实现中 `chat_completion_stream` 每次调用都新建 `httpx.AsyncClient`，800 个请求 = 800 次 TCP 握手，握手时间只计入客户端口径
2. **连接开销实测**（向同一 vLLM 发 `max_tokens=1` 请求对照，N=20）：每次新建连接 p50=72.6ms vs 复用连接 p50=63.1ms，即单次连接建立开销 ~10ms；均值差 19.8ms（新建连接偶发抖动，max 254ms）
3. **并发放大**：100 并发同时新建连接时 p50 差达 436ms（连接风暴效应），但测试中请求错峰发出，首批 100 个请求 TTFT 均值 149.5ms 反而低于稳态 700 个的 170.1ms，说明稳态差距主要来自逐请求的连接开销与客户端调度，而非启动风暴
4. **排除项**：ping RTT <1ms（排除纯网络传输）；首 chunk 仅 1~2 字符（排除 SSE 缓冲凑批）；token 数吻合（排除外部流量混入）
5. **分布形态**：客户端 p50=164ms vs 服务端拟合 p50=133.3ms，整体平移 ~31ms 且形状相似，符合"恒定加性开销"模型，而非算法差异

影响与修复：

- **影响**：e2e TTFT 是"用户真实视角"（含完整链路），与服务端口径存在系统性加性偏差；两者差值可用于诊断链路/客户端开销是否异常
- **修复**：2026-08-27 起 `llm_client.py` 改为按服务地址复用 `AsyncClient`（TCP keep-alive）：`keepalive_expiry=4s` 低于服务端 uvicorn 默认的 5s 空闲断开，客户端先主动过期避免撞上失效连接；万一仍撞上（`RemoteProtocolError` 等）则丢弃缓存重建连接重试一次（流式请求已收到部分数据时不重试，防止内容重复）。连接建立开销基本消除，两口径差距收敛到 ~15ms（剩余为请求传输、响应回程与客户端调度）

**案例四：报告"平均首字延迟"13.1s vs 真值 18.10s（报告汇总算法的时间平均失真）**

5000 字/110 并发测试（`文本测试-202608271432`）中，报告显示 vLLM 口径 TTFT 均值 13.1s，而 Prometheus counter 窗口差分（`ttft_sum` 差分 9972s ÷ `ttft_count` 差分 551）与 e2e 客户端实测（9983s ÷ 550 = 18.15s）均为 **18.1s**——服务端与客户端口径一致，报告值系统性低估 27%。

机制：旧汇总算法对**采样点的累计均值 F(t) 做时间平均**。该测试因 KV cache 打满触发持续抢占与排队，TTFT 从开局的 0.1s 单调上涨到终值 18.1s，对上涨曲线做时间平均必然低于终值。指标恒定时（如无排队的稳态测试）F(t) 是水平线，时间平均 ≈ 终值，因此该 bug 长期未暴露——**只要指标随时间漂移（排队、抢占、负载变化），旧算法就失真**。

影响与修复：

- **影响**：`ttft_avg_s`/`tpot_avg_s`/`prefix_cache_hit_rate_avg` 三个汇总值在负载漂移场景下失真（TTFT 类低估、缓升类高估），误导容量规划
- **修复**：2026-08-27 起报告均值改为**终值差分**（最后一次快照的 `sum/count` 差分之比 = F(T_end)，请求等权真均值）；测试结束时补一次最终指标抓取（`_wait_all`），保证终值覆盖最后一批完成的请求；终值缺失时回退旧的时间平均。吞吐/KV 占用等 gauge 类指标仍用采样点平均（时间平均对 gauge 是合理口径）
- **教训**：对"累计均值的序列"求平均是常见陷阱——先想清楚统计单元（请求）与平均方式（等权 vs 时间加权）是否匹配

**案例五：抢占次数定位 TTFT 长尾根因（`num_preemptions_total` 的价值）**

同一测试中，e2e TTFT p50=10.2s、p95=78.8s（31% 请求 >20s），而 TPOT 仅 33ms/字、吞吐只降 9.6%——"一旦开始处理就正常，但等首字极久"。Prometheus 抢占 counter 差分显示本轮发生 **350 次抢占**（对照测试 2000 字/100 并发为 0 次），首个抢占点在 t+60s（KV cache 涨满时刻，与理论推算 ~76s 吻合），此后 840s 内抢占速率与 waiting 队列深度同涨同落。

机制：vLLM 调度器 admit 请求时只检查其 prompt 的 KV 需求（~31 tok），但每个请求的 KV 占用随生成持续膨胀（该测试每请求峰值 ~3283 tok，110 并发合计 36 万 tok，是 KV 容量 ~15.6 万 tok 的 2.3 倍）。KV 耗尽后调度器把 running 队尾请求的 KV 整体释放、扔回 waiting 队头（RECOMPUTE 模式，重新 admit 时重算 prompt+已生成部分），腾位保住其他请求的解码。受害者重新排队的时间全部计入 TTFT，排在其后的新请求也被压队——这是 TTFT 长尾的直接来源；而被抢占请求重算的 prefill 不产出新 token，是吞吐小幅下降的来源之一。

**"累计抢占次数 > 0"即说明并发×生成长度超出 KV 容量**，应降并发、开 KV 量化（`--kv-cache-dtype fp8`）或缩短生成长度，而不是单纯加机器。

## 6. 使用建议

- **看服务端真实能力**（吞吐、延迟均值、缓存）：以 **vLLM 指标区**为准
- **看负载过程形态**（爬坡、抖动、趋势）：看**监控区**时序曲线，但短测试时忽略其吞吐数值，TTFT 分位数仅作参考
- **看用户体验**（真实链路延迟）：以 **case e2e** 为准，注意其字符口径
- **诊断 TTFT 长尾**：先看"累计抢占次数"与"排队请求峰值"——抢占 >0 或排队峰值高说明 KV 容量不足（见案例五），此时降并发/开 KV 量化即可根治，无需换更快的卡
- **交叉验证**：三者长期系统性偏差大时，优先怀疑口径差异（窗口、插值、单位），其次怀疑部署问题（Prometheus 抓取间隔、网络）

## 7. 直方图分桶误差的可选改进方案

监控区 TTFT 分位数失真的根源是 vLLM 直方图桶边界固定且过宽（0.1~0.25s 之间为 150ms 宽桶）。在**无法更改 vLLM 指标暴露**的前提下，桶边界是直方图信息量的硬上限，纯桶数据无法"测出"真分位数，但可以通过以下两个方案获得准确的分位数估计。两方案可组合使用，互相印证。

### 方案一：客户端 e2e 样本计算真分位数

**思路**：`CaseState.e2e_ttft` 已存有每个请求的实测 TTFT 原始样本（见第 3 节），对样本排序取分位数即为**真值**，无任何插值误差。当前 `to_dict` 的 e2e 聚合仅输出均值/最大值，需扩展输出 p50/p95。

**实现要点**：

- 对 `e2e_ttft` 列表排序，按 `p = sorted[floor(q × (n-1))]`（或线性插值法）取分位数
- case 级已有样本；如需全局分位数，将各 case 的 `e2e_ttft` 合并后计算
- TPOT 同理可基于 `e2e_tpot` 样本计算

**优点**：

- 精确（逐请求实测，无插值、无窗口、无采样间隔）
- 数据已有，实现成本近乎为零
- 天然包含网络链路延迟，是用户真实视角

**局限**：

- 口径为"客户端观测 TTFT"，比 vLLM 服务端口径多一层连接/网络/调度开销（实测案例见第 5 节案例三：客户端均值 167.5ms vs 服务端 130ms；连接复用改造后差值收敛到 ~15ms）
- 高并发下客户端自身可能成为瓶颈，此时反映的是"客户端+链路"而非纯服务端能力
- 单位为秒/请求，与服务端 token 口径的延迟指标不可直接对比

### 方案二：区间删失极大似然拟合（服务端视角）

**思路**：不改 vLLM 暴露，但把它的桶数据用得更聪明。延迟分布通常高度符合对数正态分布，用**区间删失（interval-censored）极大似然估计**从桶计数拟合分布参数，再从拟合分布计算分位数，替代 Prometheus 的线性插值。

**实现要点**：

1. 从 vLLM `/metrics` 拉取原始直方图桶计数（`_parse_prometheus` 已解析全量文本，扩展 `extract_vllm_metrics` 提取 `time_to_first_token_seconds_bucket` 系列即可）及 `sum`/`count` counter
2. 桶计数同样是服务启动以来的累计 counter，**扣除本轮首次采样基线**（与 tokens 差分相同的技术，见第 1 节），得到本轮桶计数
3. 以对数正态分布为模型，构造似然函数：每个样本只知"落在某桶 [le_{i-1}, le_i) 内"，其对数似然为 `log(F(le_i) - F(le_{i-1}))`；按各桶计数加权求和
4. 用 `sum/count` 差分得到的**精确均值**（如 121ms）作为锚定约束（对数正态下 `mean = exp(μ + σ²/2)`）
5. 数值优化求解 (μ, σ)（scipy.optimize），从拟合分布计算 p50 = `exp(μ)`、p95 = `exp(μ + 1.645σ)`

**效果示例**：均值 121ms、主体质量落在 [0.1, 0.25] 桶内时，拟合出的中位数约 110~125ms，直接消除 Prometheus 插值产生的 175ms 假象。

**优点**：

- 保持服务端口径（与 vLLM 指标区同源，可直接对比）
- 数学上站得住（区间删失 MLE 是处理粗直方图的标准方法），数千样本下拟合稳定，典型误差在几个百分点内
- 可同时修正 p50/p95/p99 等任意分位数

**局限**：

- 依赖"延迟服从对数正态"的分布假设；负载双峰（如冷热请求混杂、长短 prompt 混跑）时失准，需先检查桶形态是否单峰
- 需引入 scipy 做数值优化（实现约几十行代码）
- 拟合的是"本轮整体分布"，不提供时序过程（时序仍看监控区曲线）

> **状态：已实现**（未引入 scipy，用一维黄金分割搜索替代数值优化库）。引擎轮询 `/metrics` 时同步提取 TTFT 直方图桶并做基线差分；测试结束时以本轮精确均值为锚定约束拟合对数正态分布，`vllm_metrics_summary` 输出 `ttft_p50_fit_s`/`ttft_p95_fit_s`。监控区统计卡片的 TTFT p50/p95 **优先显示整轮拟合值**（标注"拟合"），无拟合数据（旧报告/拟合失败）时回退 Prometheus 插值统计；时序曲线仍为 Prometheus 插值，仅作趋势参考。验证：模拟对数正态数据（5000 样本）拟合误差 <1%；全部质量落在宽桶的极端场景下 p50 收敛到均值附近，消除桶中点假象。

### 组合建议

报告中并列展示两类分位数：**客户端实测分位数**（方案一，真值、用户视角）+ **服务端拟合分位数**（方案二，修正估计、引擎视角）。两者相互印证：数值接近时可信度高；系统性偏差时，差值即网络链路开销。

> 备注：较新版本的 vLLM 支持通过环境变量自定义直方图桶边界。若未来可重启服务端，将 0.1~0.25s 区间细分为多桶（如 10ms 步长）是釜底抽薪的解法，届时 Prometheus 原生分位数即可恢复可信。
