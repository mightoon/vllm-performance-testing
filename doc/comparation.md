# 文本生成测试对比分析（2026-08-27 ~ 2026-08-28）

> 本文记录从 2026/08/27 15:19 提问开始，围绕"2000字/100并发 无排队"与"5000字/110并发 大量排队"两次测试的对比分析，以及其后一系列验证测试的完整分析链。已剔除后续被证伪的推断。

## 1. 环境与背景

- 硬件：4 × RTX 4090（每卡 24GB），vLLM 启动时指定使用 70% 显存
- 模型：Qwen3.8（实例 c018133f，http://192.168.100.242:10138/v1），两次测试间服务端配置未换实例，但**后续证实两次测试之间服务端调度参数被重配过**（详见 §5）
- 测试方式：并发 case 各自循环请求生成指定长度文章，统计端到端 TTFT/TPOT，同时抓取 vLLM `/metrics` 快照

## 3. 原始问题逐一解答

### Q1：主要影响是文章长度还是并发？

**主因是长度，并发只是次要因素。** 机制上：每条请求的 KV cache 占用 ≈ prompt tokens + 已生成 tokens，随生成进度线性增长。KV 池总容量固定（4×24GB×70% 显存中划出的部分），因此：

- 1333：100 并发 × 平均每请求 KV 占用 → 池子 81%，有余量，全部请求随时可准入；
- 1432：单请求 KV 需求约为 1333 的 2.5 倍（5000 vs 2000 字），并发仅多 10%，但"并发 × 单请求占用"直接击穿池容量 → KV 100% 打满 → 准入被卡。

即：**文章长度通过放大单请求 KV 占用，把系统从"槽位有余"推到"KV 容量瓶颈"**。若维持 2000 字而把并发提到 110，KV 峰值约 91%（81%×1.1），大概率仍无排队——长度才是跨越临界点的那一刀。

### Q2：请求排队是因为 KV cache 打满了吗？

**1432 这次：是的。** 证据链：

1. KV 峰值 100%，且从 t≈80s 起长期钉在 99.4% 以上；
2. vLLM 的准入控制（watermark 机制）：新序列只有在"当前 KV 用量 + 预估需求 < 池容量 − watermark"时才被调度进 running，否则留在 waiting；
3. running 与 waiting 互补波动（run 76↔110，wait 33↔0），波动周期 = 长请求完成释放大块 KV → 一批 waiting 准入 → KV 再次打满；
4. 1333 作为对照组：KV 从未打满 → waiting 恒为 0。

（注意：此结论针对 1432 当时的服务端配置——按需分配模式。08/28 重配后的行为不同，见 §5。）

### Q3：TTFT 高也是在等排队吗？

**是，排队时间在 TTFT 中占绝对主导。** TTFT = 排队等待 + prefill 计算。1432 的 prefill 本身与 1333 无本质差异（prompt 都很短，几十字），但：

- p50 从 0.13s 涨到 2.68s（×20）——一半请求要等前一批完成释放 KV；
- p95 达 66.7s、max 116.6s——排在队尾的请求要等多轮"完成-释放-准入"周期；
- e2e 口径下 82.7% 的请求平均 TTFT > 10s，34.5% > 20s。

分布形态（p50 ≪ p95）正是"容量准入排队"的典型特征：不是所有请求都慢，而是**每轮能挤进去的名额有限**，挤不进去的等到天荒地老。

### Q4：逐字间隔不高、生成吞吐下降不多，是因为排队没计入生成吞吐吗？

**对，这个判断正确。** 两个口径要分开：

- **引擎侧 `gen_throughput`（vLLM /metrics）**：只统计当前 running 序列的 token 产出速率。排队中的请求不产出 token，自然不计入。所以 1432 的 avg 只从 1900 降到 1658（-13%），峰值反而 2045。
- **TPOT（逐字间隔）**：只在"首 token 之后"才计时，天然排除排队。1333 29.7ms vs 1432 31.7ms，几乎不变——说明**解码阶段本身没有劣化**。

那 -13% 的下降来自哪？来自 running 数量的波动（75~110 vs 稳定 100）：running 低谷时 GPU 批次不满，解码效率下降；KV 打满时调度器频繁尝试准入失败的开销；以及（若发生）抢占导致的重算。这是"排队拖累了平均批次大小"，而不是"生成能力下降"。

### Q5：该环境的生成能力上限基本就在 2000 tok/s 左右？

**对。** 多次测试的引擎吞吐峰值高度收敛：

| 测试 | 吞吐峰值 |
|---|---|
| 1333（2000字/100并发） | 1992 tok/s |
| 1432（5000字/110并发） | 2045 tok/s |
| 1528（100字/200并发） | avg 1744 |
| 0946（200字/200并发） | avg 1756 |
| 1015（3000字/200并发） | avg 1842 |

峰值稳定在 ~2000 tok/s，这是 4×4090（70% 显存）在该模型上的解码吞吐硬件上限。只要 running 能维持满批次，吞吐就贴着这条线；排队本身不削减这条上限，只降低平均利用率。

## 4. 深层机制：KV% 指标在不同配置下的含义

分析过程中发现一个关键事实：**`gpu_cache_usage`（KV%）的语义随服务端调度配置而变**，这直接影响了早期推断的准确性。

### 4.1 1432 时代（按需分配模式）

KV% 反映**实际 token 占用 / 池容量**。特征：

- KV 随生成进度逐渐爬升，请求完成时阶梯式回落；
- KV = 100% 是真实的内存耗尽，触发准入限制与（可能的）抢占；
- running 可以明显低于并发数（75~110 波动），因为准入由"剩余 KV 预算"决定。

### 4.2 08/28 重配后（保底分配 + max_num_seqs=127）

KV% 实测**严格等于 running/127**（0946 全部 20 个采样点精确成立，误差 < 0.01%）。含义变为**并发槽位占用率**：

- 每条序列准入时即被预留一个固定槽位（1/127 ≈ 0.79% 池容量），与实际生成到多少字无关；
- 两个生成长度差一倍的测试（1528/0946）都满足该恒等式，证明与 token 进度无关；
- 实际 token 占用远低于表观值（如 200 字场景实际约 127×200 ≈ 2.5 万 token，而表观 98%）；
- "KV 达 100%" 实为"127 个槽全部占满"，**不是内存压力**。

由此产生一个重要的推断修正（详见 §6）：重配后排队的根因不再是 KV 准入，而是 **127 的序列并发上限（max_num_seqs 类参数）**。

### 4.3 两种模式的判别方法

看 `KV% − running/127` 的差值：

- 差值 ≈ 0：保底分配，KV% 是槽位占用率，排队根因是并发上限；
- 差值显著 > 0：存在超出槽位线性的真实 token 占用，KV% 反映内存压力，排队根因是容量准入。

## 5. 验证测试时间线与发现

> 08/27 15:19 提问后，为验证各推断做了一系列控制变量测试。08/27 16:21 对监控代码做了两处修复（新增抢占计数采集等，代码变更本身不在本文记录范围），08/28 的测试均基于修复后的采集。

### 5.1 短文高并发系列（定位新配置下的排队根因）

固定 200 字，扫描并发（0914→1012）：

| 并发 | run max | wait max | KV% avg | TTFT p50 | TTFT p95 | 抢占 |
|---|---|---|---|---|---|---|
| 120 | 119 | **0** | 63.2% | 0.14s | 0.21s | 0 |
| 130 | 127 | 3 | 63.1% | 0.20s | 0.42s | 0 |
| 150 | 127 | 22 | 69.5% | 0.51s | 3.20s | 0 |
| 200 | 127 | 73 | 77.9% | 1.17s | 11.09s | 0 |
| 300 | 127 | 129 | 81.8% | 2.60s | 23.35s | 0 |

发现：

1. **并发 ≤ 127 时零排队**（120/130 档），TTFT p50 保持在 0.2s 内——体验良好；
2. **并发 > 127 后，waiting ≡ 并发 − running(≤127) 恒等式精确成立**（0946 验证：全程 waiting = 200 − running）；
3. **排队与 KV 水平无关**：0946 在 t=10~20s 时 KV 仅 37%、running=47、waiting=0；KV 均值 77.9%（远未满）时仍有 73 条排队——排队与否只取决于 running 是否触及 127；
4. **零抢占**：保底槽位使内存永不超卖，不会触发抢占；
5. TTFT 长尾是"容量内排队"：p50 1.17s / p95 11.09s，TPOT 稳定 0.059s，1200/1200 全部完成零错误，吞吐 1756 tok/s——系统不过载，只是超过 127 的请求在等槽位。

### 5.2 长文回归测试（1015：3000字/200并发）

这是对"扩并发不扩池子"风险的直接验证：

- KV 100% 打满，且 **KV% − running/127 差值达 +20~28 个百分点**——真实 token 占用远超槽位线性值，内存压力回归（§4.3 判别法）；
- running 被压到 90~119（低于 127），waiting 高达 ~100——容量准入再次成为瓶颈；
- **抢占 346 次**：保底槽位之和（127 × 槽位）小于长文实际需求时，调度器被迫抢占低优先级序列、释放其 KV 给新请求，被抢占序列重新排队重算；
- TTFT 灾难性恶化：p50 12.99s，p95 **271s**，均值 71.5s；
- 引擎吞吐 avg 1842 tok/s 仍接近上限——再次印证"排队/抢占不削减解码能力，但摧毁延迟"。

### 5.3 两次服务端配置的行为对比

| 维度 | 1432 时代（按需分配） | 08/28 重配后（保底+127上限） |
|---|---|---|
| 短文高并发表现 | — | 200 并发仅槽位排队，p95 11s，零抢占 |
| 长文高并发表现 | KV 满→准入排队，p95 67s | KV 满→准入排队+**抢占**，p95 271s |
| KV% 含义 | 真实内存占用 | 槽位占用率（短文时） |
| running 能否到 127+ | 可到 111（受 KV 限制波动） | 短文可满 127；长文被 KV 压低 |

注意：1015（346 次抢占）与 1432（当时未采集抢占数）同为"长文 + KV 打满"场景，行为模式一致，说明**只要单请求 KV 需求 × 并发超过池容量，无论哪种分配模式，排队与 TTFT 恶化都不可避免**；保底分配在短文场景更稳（零抢占），但在长文场景反而叠加了抢占惩罚。

## 7. 结论汇总

对 2026/08/27 15:19 提问的最终回答：

1. **主因是文章长度，不是并发**。长度放大单请求 KV 占用（5000 字 ≈ 2000 字的 2.5 倍），把系统推过 KV 容量临界点；并发 100→110 只是次要增量。
2. **1432 的排队确实是 KV cache 打满所致**：准入控制（watermark）在池子接近满时阻止新序列进入，形成"完成→释放→准入"的波动循环（run 76↔110 / wait 0↔33 互补波动）。
3. **TTFT 高就是排队时间**：p50 2.68s、p95 66.7s、max 116.6s，排队占绝对主导；82.7% 请求平均 TTFT > 10s。
4. **判断正确**：引擎吞吐与 TPOT 都不包含排队时间，所以逐字间隔几乎不变（29.7→31.7ms）、吞吐峰值不降反升（1992→2045）；avg 吞吐 -13% 来自 running 波动导致的批次不满，而非能力下降。
5. **判断正确**：该环境解码吞吐上限约 2000 tok/s（多次测试峰值收敛于 1992~2045）。

延伸结论：

6. **当前（08/28 重配后）配置的有效并发上限是 127**：并发 ≤ 127 时零排队、TTFT p50 < 0.2s；超过部分严格按 `并发 − 127` 排队。
7. **短文（≤200 字）场景**：200 并发下 p95 11s、零抢占、零错误，属"容量内排队"，可通过压并发到 127 以内获得 p95 < 0.5s 的体验。
8. **长文（≥3000 字）场景**：即使 127 上限也救不了——单请求 KV 需求 × 并发超过池容量时，必然回到"KV 满 → 排队 + 抢占"，1015 实测 p95 271s、抢占 346 次。
9. **吞吐与延迟解耦**：所有测试中引擎吞吐都贴近 ~2000 tok/s 上限（avg 1521~1901），排队与抢占只摧毁延迟（TTFT），不削减总吞吐。容量规划应以"延迟目标"而非"吞吐目标"驱动。

## 8. 建议

1. **短文高并发**：将客户端并发控制在 ≤127（或调大服务端 `max_num_seqs`，但须同步扩 KV 池，见下条）；
2. **若调大 `max_num_seqs`**：KV 池若是按 `127 × max_len` 配置的，扩并发而不扩池子会重新引入真实内存压力与抢占——调整后先用"200 并发 + 3000 字"验证抢占计数是否为 0（1015 已示范了失败情形）；
3. **长文场景**：按"池容量 / (prompt + max_tokens)"估算安全并发，3000 字场景安全并发约为 127 × (200/3000) ≈ 8~10 倍缩水，要么降并发要么扩显存配额；
4. **监控判别**：日常用 `KV% − running/127` 差值快速判断排队根因（§4.3），差值持续 > 10 个百分点即存在真实内存压力，需要关注抢占计数。
